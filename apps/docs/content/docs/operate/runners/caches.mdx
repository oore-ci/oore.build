---
title: 'Dependency caches'
status: implemented
description: 'How a runner keeps pub, Gradle, CocoaPods and Xcode caches between builds.'
---

Every build starts from a fresh clone. The runner keeps package manager caches between builds so a second build with the same lockfiles skips dependency downloads.

## What is cached

The runner owns one directory per tool and points build steps at it:

| Cache                | Directory         | Variable           |
| -------------------- | ----------------- | ------------------ |
| pub                  | `pub`             | `PUB_CACHE`        |
| Gradle               | `gradle`          | `GRADLE_USER_HOME` |
| CocoaPods downloads  | `cocoapods`       | `CP_CACHE_DIR`     |
| CocoaPods spec repos | `cocoapods-specs` | `CP_HOME_DIR`      |

The directories live under `~/Library/Caches/build.oore/runner-caches/<runner>/` on the Runner Mac. A pipeline variable with the same name overrides the runner's value.

Xcode keeps DerivedData in its default location. Each project builds from the same workspace path on a runner, so Xcode reuses one DerivedData folder per project.

Builds that run in a VM also use `derived-data`, one folder per project, and `android-sdk`, which holds Android SDK packages the VM image lacks. See [VM isolation](/operate/runners/vm-isolation).

Builds use the runner's Gradle home, so before each build the runner copies `~/.gradle/gradle.properties` into it. Proxy settings such as `systemProp.https.proxyHost` and JVM settings there keep applying. Edit the file in `~/.gradle`, not the copy.

## Hits and misses

After checkout, the build log lists each cache with the hash of its lockfiles: `pubspec.lock` for pub, the Gradle wrapper and settings files for Gradle, and `Podfile.lock` for CocoaPods.

- **hit**: a successful build with the same lockfiles has run on this runner, so the dependencies are already on disk.
- **miss**: the lockfiles are new to this runner, so the tools download what they need and the runner records the hash when the build succeeds.

## Size and eviction

The runner measures its caches after each build and reports the total in **Settings → Runners**. Above the cap it deletes the least recently used entries until the total is below 90% of the cap.

The cap is 50 GB. To change it, set `OORE_RUNNER_CACHE_MAX_GB` in the runner's environment. To move the caches, set `OORE_RUNNER_CACHE_DIR`.

## Purge the caches

In **Settings → Runners**, open the runner's actions and choose **Purge cache**. The runner deletes its caches and its DerivedData folders before its next build. The next build of each project downloads its dependencies again.
